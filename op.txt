That's exactly what op run with an env file is for — the same mechanism oprun wrapped, but done per project rather than globally, which is the idiomatic pattern:

1. Env-file approach (best for a script with several secrets). In the project, create a .env file containing op:// references instead of real values — it's safe to commit since there's nothing secret in it:

# .env — references, not secrets
DB_PASSWORD="op://Private/myapp prod/db_password"
STRIPE_KEY="op://Private/myapp prod/stripe_key"
GITHUB_TOKEN="op://Private/dotfiles secrets/github_token"
SOME_FLAG="plain-values-are-fine-too"

Then run the script through op run:

op run --env-file=.env -- ./deploy.sh

One Touch ID, all references resolved, and the secrets e's environment — gone when the script exits. Bonus: op
run masks the secret values if the script accidentally p --no-masking if that gets in the way).

2. Inline, no file needed — op run also resolves op:// r environment, so for a one-off:

DB_PASSWORD='op://Private/myapp prod/db_password' \
STRIPE_KEY='op://Private/myapp prod/stripe_key' \
op run -- ./deploy.sh

3. op inject — if the script insists on a real config file rather than env vars, keep a template with op:// references and render it on
demand: op inject -i config.tpl -o config.ini (then del done).

So the day you hit a multi-secret script, it's just a .project plus op run --env-file=.env -- <cmd> — no global
dotfiles machinery needed.
